# Mixtape - Bug Hunt Submission

## AI usage

I used Claude Code the whole way through, mostly for reading and tracing code and understanding functions that looked off, not for finding bugs blind.

- **Codebase orientation (Milestone 1).** I had it read `app.py`, `models.py`, every file in `routes/` and `services/`, and `seed_data.py` directly (not summarized secondhand) and explain each module's responsibility, which is what became the codebase map below. Then I had it trace the rate-a-song to notification flow end to end by reading `routes/songs.py` and `services/notification_service.py` together. That's what surfaced that `rate_song()` has no `create_notification()` call while `add_to_playlist()`, right above it in the same file, does. A pretty visible asymmetry once you're looking at both functions side by side, not a guess.
- **Reproducing bugs (Milestone 2).** For each issue I had it write a minimal standalone Python reproduction script (spin up an in-memory DB, set up the exact state described in the issue, call the service function, print the result) instead of asking it to predict what would happen. I ran every single one of these myself and read the actual output before deciding a bug was confirmed. That's how I found out Issue #3 doesn't actually reproduce as reported. I saw `len(results) == 1` when I expected 2 or 3, asked it why, and it correctly pointed out that `db.session.query(Song)...outerjoin(song_tags)` returns full `Song` entities, and SQLAlchemy's ORM identity map collapses duplicate rows sharing a primary key even though the underlying SQL joins produce one row per tag. I checked this myself too by printing the `id` values on the "duplicate" rows and confirming they really were the same object, not just taking its word for it.
- **Understanding specific functions.** For `update_listening_streak()` I asked "what edge cases could cause this to return the wrong value" after I'd already read through the function and noticed the odd `weekday() != 6` clause. It confirmed that clause has no real justification (it's not computing an ISO week boundary or anything, just excluding one weekday from the increment branch) and that just removing it was the minimal fix, which lined up with what the existing `test_streak_increments_on_sunday` test (already in the repo, already failing) expected.
- **Where I pushed back instead of just going with it.** For Issue #2, its first suggestion was to keep a rolling window but shrink it down to something like 30-60 minutes, reasoning from the "listening now" name and the seed_data.py comments about 10-25 minute vs 2+ hour events. I didn't go with that. The issue report explicitly contrasts "today" against "yesterday evening," which is a calendar-day distinction, not a duration one. A 30-minute window would still hide a friend's listen from 3 hours ago earlier the same day, and nobody's complaining about that. So I went with a calendar-day boundary instead and had it implement that version. I also asked it to write a regression test with a frozen clock straddling a real day boundary (11pm one day to 9am the next, about 10 hours apart), specifically because a naive test comparing "yesterday" to "today" relative to `datetime.now()` wouldn't reliably catch a rolling-window bug depending on what time the suite happens to run.
- **Where I didn't rely on it at all:** every fix's actual root cause got confirmed by me running the reproduction script or the test suite myself and reading the before/after output before I wrote up the RCA below. "This looks like the bug" wasn't good enough on its own without actually watching it fail and then pass.

## Overview

Mixtape is a Flask + SQLAlchemy app. Friends share songs, build collaborative playlists, rate songs, and see what their friends are listening to. The app is organized as a thin routes -> services -> models stack: routes parse HTTP input and return JSON, services hold all the business logic, and models define the schema.

## Main files

- **`app.py`** - Application factory (`create_app`). Sets the DB URI and secret key, initializes the shared `db` (Flask-SQLAlchemy) object, registers the four blueprints (`songs`, `playlists`, `users`, `feed`) under their URL prefixes, and calls `db.create_all()`. This is also where the shared `db` instance lives, meaning every model and service imports `db` from here, which is why `models.py` imports `from app import db` instead of the other way around.

- **`models.py`** - All SQLAlchemy models and association tables:
  - `User` - has a `listening_streak`/`last_listened_at` pair, plus relationships to shared songs, ratings, listening events, notifications, playlists, and a symmetric many-to-many `friends` self-relationship (via the `friendships` table).
  - `Song` - title/artist/album/genre, who shared it (`shared_by`) and when, plus many-to-many `tags`.
  - `ListeningEvent` - a timestamped record of a user listening to a song. This is the source of truth for streaks and feeds.
  - `Rating` - a user's 1-5 score for a song (unique per user/song pair).
  - `Playlist` - name, creator, `is_collaborative` flag, and many-to-many `songs` via the `playlist_entries` table, which also stores `position`, `added_by`, and `added_at`. So playlist ordering is tracked as association-table metadata, not on `Song` itself.
  - `Notification` - a typed, readable/unread message to a user.
  - Every model has a `to_dict()` used to serialize straight to JSON in routes; there's no separate serializer layer.

- **`routes/`** - One blueprint per resource. Each route function pulls params from `request`, calls exactly one service function, and turns a `ValueError` into a 4xx JSON response. Routes have no business logic in them.
  - `songs.py` - `/songs/search`, `/songs/<id>`, `/songs/<id>/rate` (POST), `/songs/<id>/listen` (POST).
  - `playlists.py` - `/playlists/` (POST create), `/playlists/<id>`, `/playlists/<id>/songs` (GET/POST).
  - `users.py` - `/users/<id>`, `/users/<id>/streak`, `/users/<id>/notifications`, `/users/notifications/<id>/read` (POST).
  - `feed.py` - `/feed/<id>/listening-now`, `/feed/<id>/activity`.

- **`services/`** - All business logic lives here; also where the tracked bugs live.
  - `streak_service.py` - `record_listening_event()` creates a `ListeningEvent` and calls `update_listening_streak()`, which compares `last_listened_at` to today: same day means no change, exactly one day gap means increment, anything else resets to 1.
  - `feed_service.py` - `get_friends_listening_now()` returns each friend's most recent song within a rolling 24-hour window (deduped to one entry per friend); `get_activity_feed()` returns the most recent N events from friends with no time filter at all.
  - `search_service.py` - `search_songs()` does a case-insensitive title/artist substring match, `get_song()` fetches one song by id.
  - `notification_service.py` - `create_notification()` is the shared notification writer; `add_to_playlist()` appends a song to a playlist then notifies the original sharer (skipping self-notifications); `rate_song()` upserts a `Rating`; `get_notifications()`/`mark_as_read()` handle retrieval and read state.
  - `playlist_service.py` - `create_playlist()`, `get_playlist()` (metadata only), `get_playlist_songs()` (songs ordered by `position`), `get_user_playlists()`.

- **`seed_data.py`** - Populates the DB with sample users/songs/playlists for manual testing.

- **`tests/`** - `test_streaks.py`, `test_search.py`, `test_playlists.py` exercise the corresponding services directly (not through HTTP), which matches the routes-are-thin design. During the bug hunt I added `test_feed.py` and `test_notifications.py` since those two services didn't have any tests.

## Data flow: rating a song -> notification (traced, not just guessed)

This is the flow that's supposed to produce a notification on both add-to-playlist and rate, per the issue list. Tracing it end to end is exactly what shows why only one of those two paths actually does it.

1. Client calls `POST /songs/<song_id>/rate` with `{user_id, score}`.
2. `routes/songs.py::rate()` checks that `user_id`/`score` are present, then calls `services.notification_service.rate_song(user_id, song_id, score)`.
3. `rate_song()` checks the score is 1-5, loads the `Song` and `User`, and upserts a `Rating` row (`existing.score = score` if already rated, otherwise creates a new one). Commits and returns.
4. `rate_song()` never calls `create_notification()`. Compare that with `add_to_playlist()` in the same file, which after appending the song to the playlist explicitly calls `create_notification()` to alert `song.shared_by` (skipping the case where the sharer added it themselves). `rate_song()` has no equivalent call, so the song's original sharer never finds out their song got rated. This lines up exactly with open issue #4 ("notified when added to playlist but not when rated").
5. Separately, notifications get read via `GET /users/<id>/notifications` -> `routes/users.py::notifications()` -> `notification_service.get_notifications()`, which just filters/orders `Notification` rows. No logic bug there, it's purely that `rate_song()` never inserts the row in the first place.

## Patterns noticed

- **Strict layering, nothing leaks upward.** Every route follows the same shape: parse request, call one service function, catch `ValueError`, return JSON. Business rules never show up in `routes/`, which makes "where does X happen" an easy question to answer, it's always in `services/`.
- **`ValueError` is the one signal for "not found" or "invalid input."** Services raise it, routes catch it uniformly and turn it into a 400/404. No custom exception hierarchy.
- **Association tables carry metadata, not just link rows.** `playlist_entries` stores `position`/`added_by`/`added_at`, so playlist ordering and attribution live in the join table, not on `Song` or `Playlist`. Any bug about playlist order or "who added this" should point you at queries against `playlist_entries`, not the models directly.
- **`to_dict()` on every model doubles as the API's serialization layer.** No separate schema/serializer, so response shape changes happen by editing the model itself.
- **Time-window logic gets duplicated with different assumptions.** `feed_service.get_friends_listening_now()` uses a 24-hour rolling window (`now - 24h`), while the issue describing it talks about "yesterday," which is a calendar-day boundary, not a rolling window, and those two disagree near day boundaries. `streak_service.update_listening_streak()` has its own separate date-boundary logic too (including a special-cased `today.weekday() != 6` check for Sundays) that shares no code with the feed's time logic. Each service just reinvents "what counts as recent" on its own. Both were worth double checking against the exact issue wording before fixing.
- **Off-by-one/slicing risk in list-returning services.** `get_playlist_songs()` builds the fully ordered song list and then returns `songs[:-1]`, silently dropping the last entry. Worth checking against the "last song in a playlist never shows up" issue.
- **Search joins can multiply rows.** `search_songs()` does an `outerjoin` against `song_tags` but selects `Song` objects and never groups or dedupes, so a song with multiple tags could in theory show up once per tag row it matches. Worth checking against the "same song shows up twice" issue.

## Root cause analysis

### Issue #1 - My listening streak keeps resetting (Sundays)

**How I reproduced it.** Wrote a standalone script that spins up an in-memory DB, a fresh `User`, and calls `update_listening_streak()` directly with a Saturday `datetime` (UTC) followed by a Sunday `datetime` one calendar day later. Before any fix, the streak went from 1 to 1 instead of 1 to 2. This matches the existing `tests/test_streaks.py::test_streak_increments_on_sunday` test, which was already in the repo and already failing. I ran `pytest tests/test_streaks.py -v` and confirmed it failed with `assert 1 == 2` before touching any code.

**How I found the root cause.** Started at `routes/songs.py::listen()` -> `services/streak_service.py::record_listening_event()` -> `update_listening_streak()`, following the README's suggested navigation pattern. Reading `update_listening_streak()` line by line, the branch structure is: same day means no-op, one day gap means increment, anything else means reset. The increment branch read `elif days_since_last == 1 and today.weekday() != 6:`, and that `and today.weekday() != 6` is what made me stop, since nothing in the streak rules (stated right there in the function's own docstring) mentions excluding a specific weekday. I confirmed this was the exact trigger by checking that `datetime(2024, 6, 16).weekday()` (a Sunday) equals `6`, so any one-day-gap listen landing on a Sunday failed that `and` condition and fell through into the `else: user.listening_streak = 1` branch instead.

**The root cause.** `update_listening_streak()` had an extra condition, `today.weekday() != 6`, tacked onto the "exactly one day since last listen" increment branch. `datetime.weekday()` returns `6` for Sunday, so this condition evaluates to `False` every single Sunday no matter what, regardless of whether the user actually listened the day before. That routes every Sunday listen with a valid one-day gap straight into the `else` branch, which unconditionally resets the streak to 1, which is exactly kenji's report of a 12-day streak collapsing to 1 specifically on Sundays and then resuming normal incrementing on Monday (where `weekday() != 6` is `True` again, so the next day's increment worked fine and pushed the reset 1 up to 2).

**Fix and side-effect check.** Removed the `and today.weekday() != 6` clause entirely, leaving `elif days_since_last == 1:` as the only condition needed to increment. Ran the full `tests/test_streaks.py` suite afterward, all 5 tests pass, including same-day no-op, consecutive-day increment, skipped-day reset, and the Sunday case. I also walked through the other weekdays by hand (Monday through Saturday all had `weekday() != 6` as `True` already, so their behavior doesn't change). This fix only changes behavior for the one weekday that was actually broken.

### Issue #2 - Friends Listening Now shows people from yesterday

**How I reproduced it.** Wrote a script with two friended users; one (`darius`) got a `ListeningEvent` timestamped 10 hours in the past, simulating "11pm last night" checked at "9am this morning." Calling `get_friends_listening_now(nova.id)` returned darius in the feed. A rolling 24-hour window doesn't distinguish "10 hours ago, still yesterday" from "10 hours ago, earlier today."

**How I found the root cause.** Traced `routes/feed.py::listening_now()` -> `services/feed_service.py::get_friends_listening_now()`. The function computes `cutoff = datetime.now(timezone.utc) - RECENT_THRESHOLD` where `RECENT_THRESHOLD = timedelta(hours=24)`, then filters `ListeningEvent.listened_at >= cutoff`. That's a sliding 24-hour window anchored to the current moment, not a calendar-day boundary. I confirmed this was the actual cause, not just something that looked suspicious, by doing the math on the 11pm/9am example from the issue: 9am minus 11pm the day before is 10 hours, comfortably inside a 24-hour window. So the rolling window mathematically can't exclude that event no matter what else the function does.

**The root cause.** `get_friends_listening_now()` defines "recent" as "within the last 24 hours of wall-clock time" instead of "since midnight today." Those only line up at exactly midnight. A listen at 11pm yesterday is 10 hours old at 9am today, which is inside a 24-hour window, so it shows up, but it's still "yesterday" by calendar date, which per the feature's own name and the issue report is exactly what shouldn't show. It's a mismatched definition of "recent," not a broken comparison somewhere.

**Fix and side-effect check.** Changed the cutoff from `now - 24h` to `now.replace(hour=0, minute=0, second=0, microsecond=0)`, meaning midnight UTC of the current day, so the filter becomes "has this friend listened to anything since today started," which matches the issue's own "today" vs "yesterday evening" framing. Removed the now-unused `RECENT_THRESHOLD` constant and the `timedelta` import. Verified with a new deterministic test (`tests/test_feed.py::test_listen_from_yesterday_evening_does_not_appear_this_morning`) using a frozen clock that straddles a real day boundary (Mon 11pm -> Tue 9am). I confirmed it actually fails against the pre-fix rolling-window code by stashing the fix and rerunning it, it failed with the yesterday event still showing up, and it passes after the fix. I also checked `get_activity_feed()` in the same file, which has no time filter at all and wasn't touched, and confirmed the same-day case (`test_listen_from_earlier_today_appears`) and the no-friends case (`test_no_friends_returns_empty_list`) still pass.

### Issue #3 - The same song keeps showing up twice in search (investigated, not reproducible)

**How I reproduced it (attempted).** Wrote a script creating a song with three tags (`Crown Heights Anthem` / `Borough Kings`, the exact example from the issue) and called `search_songs("Anthem")`. Result: `len(results) == 1`, not 2 or 3. I also ran the pre-existing `tests/test_search.py`, which already has `test_search_no_duplicates_multi_tag_song` asserting exactly this scenario returns 1 result, and it passed before I changed anything.

**How I investigated.** Traced `routes/songs.py::search()` -> `services/search_service.py::search_songs()`. The query does `db.session.query(Song).outerjoin(song_tags, ...)` with a title/artist filter and `.all()`. The `outerjoin` against `song_tags` really does produce one SQL row per matching tag for a multi-tag song, I confirmed that by printing the `.statement` and checking the join multiplies rows at the SQL level, so at the raw-SQL level this looks exactly like the reported bug. But `query(Song)` selects full `Song` entities, not raw columns, and SQLAlchemy's ORM identity map dedupes entity results that share a primary key when it materializes `.all()`. So the duplicate SQL rows collapse back down into one `Song` object per unique `id` before `to_dict()` ever runs.

**The root cause (or lack thereof).** There's a code smell here, the query joins on `song_tags` for no real purpose (`Tag` isn't even selected or filtered on), and it would produce actual duplicate output if the query ever got changed to select raw rows/columns instead of ORM entities. But as it's currently written, it doesn't reproduce the reported symptom, and I couldn't find any input (different tag counts, duplicate tags, songs sharing a title) that made it duplicate under the current `db.session.query(Song)` shape.

**Fix and side-effect check.** Added `.distinct()` to the query anyway, as a defensive measure. It's a no-op right now since the ORM was already deduping, but it makes the query correct on its own instead of relying on identity-map behavior to bail it out. Ran the full `tests/test_search.py` suite after the change, all 5 tests still pass, including the multi-tag, single-tag, and no-tag duplicate checks. I'm documenting this as "could not reproduce as reported," per the assignment's own guidance to try a different issue if reproduction fails, rather than inventing a root cause that doesn't match what I actually observed.

### Issue #4 - Notified for playlist adds but not for ratings

**How I reproduced it.** Wrote a script with a song shared by `aaliya` and rated by `kenji` via `rate_song(kenji.id, song.id, 5)`, then checked `get_notifications(aaliya.id)`. Result: 0 notifications, confirming the rating does save (like aaliya's report says, "it shows on the song") but no notification gets created. I also called `add_to_playlist()` with the same setup to confirm that path does produce a notification, so I could compare the two directly.

**How I found the root cause.** Both functions live in `services/notification_service.py`. Reading `add_to_playlist()` top to bottom: it appends the song to the playlist, commits, then has an explicit block, `if song.shared_by != added_by_user_id: create_notification(...)`. Reading `rate_song()` right below it: it checks the score, upserts the `Rating`, commits, and returns. No call to `create_notification()` anywhere in `rate_song()`. The second I put the two functions side by side, the missing block was obvious, not "the notification logic is subtly wrong somewhere," just "the notification call was never written for this path."

**The root cause.** `rate_song()` never calls `create_notification()`. `add_to_playlist()` and `rate_song()` do basically the same shape of thing, an actor acts on a resource someone else owns and that owner should get notified unless they're the one who did it, but only `add_to_playlist()` actually has the notify step. This isn't a conditional bug or an edge case, the code path to notify the sharer on a rating just doesn't exist.

**Fix and side-effect check.** Added the same kind of check used in `add_to_playlist()`, `if song.shared_by != user_id: create_notification(...)`, after the rating commit in `rate_song()`, using a new notification type `"song_rated"` and a body string following the same pattern as the playlist one. Wrote `tests/test_notifications.py` covering: rating someone else's song notifies them, rating your own song doesn't self-notify, and re-rating (the upsert path) still notifies each time. Ran the full test suite afterward, everything passes, including the untouched playlist-add, search, streak, and feed tests, which confirms this change is purely additive and doesn't touch the rating upsert logic itself (the score still saves/updates the same way; the notification is just a side effect tacked on after the existing commit).

### Issue #5 - The last song in a playlist never shows up

**How I reproduced it.** Ran the pre-existing `tests/test_playlists.py::test_playlist_returns_all_songs`, which seeds a playlist with 5 songs and asserts `get_playlist_songs()` returns 5. Before any fix it failed with `assert 4 == 5`. I also confirmed the "moving target" behavior darius described, adding a 6th song and re-fetching, by extending the manual reproduction script to add a song after the initial fetch and re-checking the count, which stayed one below the true total each time.

**How I found the root cause.** Traced `routes/playlists.py::get_songs()` -> `services/playlist_service.py::get_playlist_songs()`. The function builds `songs` via a join against `playlist_entries` ordered ascending by `position`, which is correct. The return statement was `return [song.to_dict() for song in songs[:-1]]`. That `[:-1]` slice was the moment I knew I had it. It's not a query bug, the SQL correctly fetches all songs in order, it's a post-query slice that unconditionally drops the last item off an already-correctly-ordered list no matter how many songs there are. That explains exactly why "the missing one is always whatever was added most recently" (highest `position`, last in the ascending list) and why adding a new song "frees" the previous one (it's no longer last, so it's no longer the one getting sliced off).

**The root cause.** `get_playlist_songs()` queries and orders the songs correctly, then returns `songs[:-1]` instead of `songs`, silently chopping off the last (most recently added) song from every playlist response no matter the playlist size, and directly contradicting the docstring right above it that says "this function returns all songs in the playlist."

**Fix and side-effect check.** Changed `songs[:-1]` to `songs`. Ran `tests/test_playlists.py`, all 3 tests pass: `test_playlist_returns_all_songs` (5 songs), `test_playlist_returns_songs_in_order` (exact title ordering), and `test_empty_playlist_returns_empty_list` (an empty playlist still returns `[]` instead of erroring on an empty-list slice, which was worth checking specifically since `[][:-1]` is also `[]`, meaning this bug was silent for empty and single-song playlists in a way that could've hidden it; a single-song playlist would've returned `[]` instead of `[song]` before the fix, which I checked by hand too).

## Regression test

The regression test that would most clearly have caught this before it shipped is [`tests/test_feed.py::test_listen_from_yesterday_evening_does_not_appear_this_morning`](tests/test_feed.py). It freezes `datetime.now()` to two fixed timestamps eleven hours apart that straddle a real calendar-day boundary (Monday 11pm -> Tuesday 9am) and asserts the feed comes back empty. I checked it actually catches the original bug by stashing the fix and rerunning the test suite, it failed with the stale rolling-window logic (`assert [...] == []`, showing darius's yesterday-evening listen leaking through) and passed once the calendar-day cutoff was in place. A naive test comparing "yesterday" to "today" using `datetime.now()` directly wouldn't reliably catch a rolling-window vs calendar-day bug depending on what wall-clock time the suite happens to run at, which is why this test freezes both ends of the comparison to fixed timestamps instead.
